GhostLap is a top-down 2D time-trial racer (libGDX, Java). Players race one track, and their best lap is saved as a "ghost" that other players can race against. Java Spring Boot microservices handle accounts, lap submission, server-side lap validation (anti-cheat), leaderboards and ghost storage.

## Game design
**Track**
- One closed loop built from about 12 control points using libGDX `CatmullRomSpline<Vector2>`.
- Constant width. Inner and outer edges are computed by offsetting along the spline normals.
- About 8 checkpoints spaced evenly along the spline. A lap counts only if checkpoints are crossed in order.

**Car (arcade top-down physics)**
- State: `position` (Vector2), `velocity` (Vector2), `heading` (radians).
- Inputs: throttle, brake, steer.
- Split velocity into forward and lateral components. Lateral grip below 100% gives a small drift.
- Off-track means heavy drag. There are no walls.
- `MAX_SPEED` and other constants live in `shared/ghost-format` (`GameConstants`).

**Loop**
- Fixed-timestep physics at 60 Hz using an accumulator. Rendering interpolates between physics states.

**Ghost**
- Record `(x, y, heading)` every 2 physics ticks (30 Hz).
- Playback interpolates position linearly and heading along the shortest angle.
- The ghost car is drawn semi-transparent.

**Screens:** Login → Menu → Race → Results/Leaderboard.

**Debug overlay (toggle F3):** FPS, frame time, Java heap usage, speed, current checkpoint.

## Ghost binary format (shared/ghost-format)
1. Header:
   - magic `GHST` (4 bytes)
   - version (byte)
   - trackId (int)
   - sampleRateHz (short)
   - sampleCount (int)
   - lapTimeMs (int)
2. Samples: `float x, float y, float heading`, repeated `sampleCount` times.
3. The whole payload is gzipped. When sent in JSON it is base64-encoded.

Provide `GhostCodec.encode/decode` with round-trip unit tests.

## API contract (v1)
Errors use Spring `ProblemDetail` (RFC 7807). Document every endpoint in `docs/API.md` and in Swagger UI.

**player-service**
- `POST /api/v1/auth/register {username, password}` → 201 `{playerId, token}`. Passwords are stored with BCrypt.
- `POST /api/v1/auth/login {username, password}` → 200 `{playerId, token}`
- `GET /api/v1/players/me` → `{playerId, username, createdAt}`

**race-service**
- `POST /api/v1/laps {trackId, lapTimeMs, checkpointTimesMs[], ghost}` → 201 `{lapId, status: ACCEPTED|REJECTED, reason?, rank?}`
- `GET /api/v1/tracks/{trackId}/leaderboard?limit=10` → `[{rank, username, lapTimeMs, lapId}]`
- `GET /api/v1/tracks/{trackId}/ghosts/top` → best accepted ghost (base64) plus metadata
- `GET /api/v1/laps/{lapId}/ghost` → that lap's ghost

## Server-side lap validation (anti-cheat)
Decode the ghost and reject the lap with a reason code if any of these fail:
- `SAMPLE_COUNT_MISMATCH`: sample count doesn't match lapTimeMs × sampleRate (±2 samples).
- `SPEED_EXCEEDED`: speed between any two consecutive samples is above `MAX_SPEED × 1.1`.
- `CHECKPOINT_ORDER`: checkpoint times are not strictly increasing, or their count is wrong.
- `TOO_FAST`: lapTimeMs is below the track's minimum plausible time.
- `BAD_GHOST`: corrupt or undecodable ghost data.

Rejected laps are stored with their reason and never reach the leaderboard. Each rule has its own unit test.

## Observability
- Actuator `health` and `prometheus` endpoints on both services.
- Custom metrics: `ghostlap_laps_submitted_total`, `ghostlap_laps_rejected_total{reason}`, and a lap validation timer.
- Every request gets a request ID, which is included in all log lines.
- A Grafana dashboard is provisioned from a file in `infra/grafana`, so it appears automatically on `docker compose up`.
